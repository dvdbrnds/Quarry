This was discovered and "fixed" at least three separate times across different features: sponsor permit deletion, general delete operations, and field name filtering. Root Cause Analysis

1. No staging environment matching production infrastructure
Clusters affected: WAF/firewall (10 commits), CSP fixes (3), Stripe webhooks (8), branding storage (5). The WAF issue alone was rediscovered three separate times because there's no pre-production environment behind Moravian's firewall. Every HTTP method restriction, CSP rule, and webhook failure was found only after deploying to production.
2. Camera/OCR pipeline has no architectural boundaries
Clusters affected: OCR/exposure (15 commits), external camera (8), QR scanner (6), image rotation (5). The BirdDog camera system treats capture, exposure, OCR, and UI as one monolith. Fixing exposure starves OCR. Pausing OCR breaks the menu button. USB reconnection requires rebuilding the entire session. These 34 commits share one root cause: everything flows through one undifferentiated pipeline.
3. Business rules implemented directly as code without specs
Clusters affected: After-hours access (8), freshmen exclusion (5), refund matching (7), lottery config (5). When business rules live only in code and there's no written spec, every policy clarification becomes a code change. The freshmen exclusion went through six different implementations in one day because the rule wasn't decided before coding started.
4. Errors silently swallowed throughout the stack
Clusters affected: Stripe (8), audit trail (7), capacity audit (7), scheduled backups (5). A recurring pattern: something fails silently → add diagnostic endpoint → discover the real error → fix it. At least four clusters started with "surface actual error instead of silently swallowing." Errors should fail loudly by default.
5. No database migration discipline
Clusters affected: Startup deadlocks (4), lot normalization (4), calculated capacity (4), branding storage (5). Migrations run in the app startup path, race with other queries, and break on container redeploys. There's no proper migration runner (like Alembic) managing ordering, locks, and idempotency.
6. No test coverage for time-based and matching logic
Clusters affected: After-hours access (8), refund matching (7), program/visitor filter (5), waitlist position (4). These are deterministic, testable functions that got re-fixed because nobody could verify the fix without deploying. A handful of unit tests would have caught every regression in these clusters.

Refactoring Recommendations

R1. Extract a BirdDog CameraManager protocol with pluggable sources
Create an abstraction layer separating camera capture (built-in, USB external, reconnect logic) from the OCR pipeline and the UI. The camera source becomes a state machine with explicit states: discovering → configuring → streaming → paused → reconnecting. OCR subscribes to frames without knowing the source. This prevents the cascade where fixing USB reconnection breaks OCR, or pausing OCR breaks the camera. Estimated savings: prevents ~34 commits of rework patterns from recurring.
R2. Create a WAF compatibility layer and document all restrictions
Write a shared WAF_RESTRICTIONS.md documenting every known blocked HTTP method and field name pattern. Build a small middleware or API client wrapper that automatically routes DELETE/PATCH through POST with method override headers, or through dedicated endpoints. Add a CI check that flags any new DELETE or PATCH route. Estimated savings: prevents 10+ commits from recurring and eliminates the #1 source of production-only failures.
R3. Add Alembic for database migrations
Replace startup-path DDL with Alembic migrations that run before the app boots, with proper lock management and idempotency. This eliminates deadlocks during startup, schema drift between deploys, and the "add missing column" pattern that appears in at least 6 commits. Estimated savings: prevents deadlock/schema clusters (~12 commits).
R4. Extract business rules into a configurable rules engine
After-hours access, freshmen exclusion, lot access by permit type, and capacity calculations should all be data-driven rules stored in the database, not hardcoded logic. An admin UI for rules means policy changes don't require code deploys. Define the rule schema: condition (time window, class year, permit type) → action (allow/deny lot access). Estimated savings: prevents 20+ commits of business-rule churn.
R5. Add a global error handling policy: fail loud by default
Audit every try/except: pass and every silent error swallow in the codebase. Replace with structured error logging to Axiom (already planned). Add a FastAPI exception handler that returns full error details in dev/staging and sanitized messages in production. Estimated savings: eliminates the "add diagnostic endpoint to find the real error" pattern (~15 commits).
R6. Write unit tests for the top 5 rework areas
Targeted test coverage, not blanket coverage. Focus on: time-window access logic (boundary conditions at 4 PM, midnight, timezone edges), permit matching and normalization (lot codes, refund matching, filter logic), capacity calculations, and the startup migration sequence. This is maybe 200 lines of tests that would have prevented ~30 commits of rework. Estimated savings: highest ROI of any recommendation.
